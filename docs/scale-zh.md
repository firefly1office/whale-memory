# 规模与观测（阶段 3）

这一轮解决的是"库变大之后"和"出了事怎么知道"两件事。所有数字都是本机实测，命令附在最后，
可以自己复跑。数据和评测语料一样是**虚构的**，不碰真实记忆。

## 一、读路径：从"整读成一个数组"到"逐条、分页"

以前 `loadAll` 是 `readFileSync` 整读再 `split('\n')`：十万条时同时占着
**文件字符串 + 切出来的行数组 + 解析后的对象**三份内存。现在：

| 接口 | 是什么 | 什么时候用 |
| --- | --- | --- |
| `loadAll(dir, opts)` | 老接口，**签名与语义一个字没改**。内部逐行读、边解析边收集 | 召回、单条读、书、导出——所有"要一次性拿到全部"的地方 |
| `iterate(dir, opts)` | 异步生成器，一条一条给；内存只跟一份小索引走 | 批量处理：导出、备份、体检、搬家 |
| `page(dir, { limit, after })` | 游标分页，一次只读这一页的字节 | 宿主想"一页一页给用户看" |

三条路径**读出来的每一条逐字段相同**，不是"差不多"：出处（`refsInfo`）、反向引用
（`citedBy`）、事后联想（`links`）、人生章节（`chapters`）、封存、想起次数、结案状态、
重复 id、旧格式 id 的认领、`asOf`，全部对拍过。这一点有 10 条用例守着
（`tests/scale-read.test.mjs`），另有一条 1000 轮的随机库属性测试（`tests/jsonl-fuzz.test.mjs`）。

### 实现要点（给后来改这行代码的人）

- **逐行读**（`packages/core/lib/jsonl-stream.js`）：按 64KB 块读，**按字节找 0x0A**。
  0x0A 不可能出现在多字节 UTF-8 序列内部，所以"按字节切行"和"先整体解码再按 `\n` 切"
  得到的是同一组行；每行单独解码，文件末尾截在多字节字符中间时最后一行解成 U+FFFD，
  和 `readFileSync` 一样。同步（`loadAll` 用）和异步（`iterate`/`page` 用）共用同一个切行器。
- **坏行口径没变**：只跳过 `trim()` 后为空的行，解析的是**原样那一行**（行首带 BOM 的行照旧算坏行）。
  `loadAll` 仍然 fail closed，且报的是**总行数**（先数完再抛）。
- **`iterate` 要读两遍文件**：跨行字段（谁的出处指向谁、谁被引用）需要知道"别处还有哪些 id"。
  `loadAll` 一遍就够，因为它本来就持有全部记录；逐条读不持有，所以第一遍建索引、第二遍产出。
  代价是时间大约翻倍（见下面的数字），换来的是内存不随正文增长。
- **索引里只有"指路"要用的东西**：id、日子、正文前 24 字、封存状态、重复/旧 id 标记、
  这一行在文件里的字节位置。**正文不进索引**——这是内存能降下来的原因。
- **`page` 的索引按文件认库**：键是「经历文件 size + mtime + asOf」，没变就直接用上一次的索引
  （只留最近一份，换目录/文件一变就重来）。不加这个的话每翻一页都要重扫全文件，十万条下
  就成了 O(n²)。事件文件每次仍现读，所以封存状态不会停在建索引那一刻。
- **遍历期间文件被改**：两遍读到的记录数对不上就抛 `EXPERIENCE_CHANGED`，不静默少返一条。
  要"同一时刻的一次性快照"请用 `loadAll`。
- **`page` 的游标**：`after` 收上一页最后一个 id；也收 `page` 自己返回的 `{ id, n }`。
  `n` 是"从这个 id 第一次出现走到这一页最后一行"的条数——文件里真有重复 id 时，
  只给 id 字符串分不清是第几条（契约里 id 永不复用，所以正常数据两种都行）。
  游标找不到就抛 `PAGE_CURSOR_UNKNOWN`，不静默从头开始（那会把一页重复一遍）。
- **两个后端的差别只在记录从哪来**：`backend: 'sqlite'` 时 `iterate`/`page` 退回整库快照
  （sqlite 的快照本来就整库进内存），结果与 `loadAll` 逐条相同，但没有内存收益。

## 二、十万条的数字

`node tools/bench-scale.mjs`（每项都在**独立子进程**里量，峰值取 `process.resourceUsage().maxRSS`；
单次运行，避免"垃圾还没回收"把峰值顶高）。

数据：10 万条虚构经历，正文长短不一，约 37 MB；其中 30% 有想起事件、5% 有后记、3% 被封存。

| 项 | 中位 | p99 | 单次峰值 RSS | 比基线多 |
| --- | --- | --- | --- | --- |
| 全量读 `loadAll` | 472.6 ms | 631.2 ms | 298 MB | **+254 MB** |
| 逐条读 `iterate` | 942.1 ms | — | 218 MB | **+174 MB** |
| 分页 `page(limit=100)` | 39.3 ms/页 | 507.3 ms（第一页含建索引） | 162 MB | +118 MB |
| 召回 `recall(limit=5)` | 887.7 ms | 1101.3 ms | 327 MB | +283 MB |
| 写入 `addExperience` | 6.9 ms | 21.6 ms | 49 MB | +5 MB |

基线子进程（只 import 模块 + 摸一下文件）44 MB。

**分页与全量切片逐条一致：10 万条全对**（基准里自带这一步校验，不一致就退出 1）。

### 峰值不是最要紧的，"最少要多少堆"才是

峰值 RSS 会被"还没回收的临时垃圾"顶高，所以两个数字差距只有 1.5 倍。真正决定能不能用的是
**V8 堆上限**（堆里活着的对象超了就直接 OOM）。同一份数据，一次读用不同的
`--max-old-space-size` 跑：

| 读法 | 能跑完的最小堆 | 结论 |
| --- | --- | --- |
| `loadAll` | **≥ 128 MB** | 112 MB 就 OOM |
| `iterate` | **≥ 80 MB** | 64 MB 就 OOM |

也就是说：十万条的记忆库，`loadAll` 至少要 128 MB 堆，`iterate` 80 MB 就够。

### 对照组：把正文写长（`--text 1000`）

同样是 10 万条，但每条正文多塞约 1000 字（文件 37 MB → **323 MB**）：

| 项 | 中位 | 单次峰值 RSS | 比基线多 |
| --- | --- | --- | --- |
| 全量读 `loadAll` | 1407.6 ms | 507 MB | +463 MB |
| 逐条读 `iterate` | 2419.7 ms | 240 MB | +196 MB |
| 分页 `page(100)` | 29.9 ms/页 | 219 MB | +175 MB |
| 召回 `recall(5)` | 9214.9 ms | 541 MB | +497 MB |

| 读法 | 正文约 370 字节/条 | 正文约 3.2 KB/条 |
| --- | --- | --- |
| `loadAll` 堆下限 | ≥ 128 MB | **512 MB 也跑不完** |
| `iterate` 堆下限 | ≥ 80 MB | **≥ 80 MB**（没变） |

这就是这一轮真正想拿到的东西：**`iterate` 压着的量只跟"有多少条"有关，跟正文多长无关**
（索引里只留 id、日子、前 24 字）。`loadAll` 则必须把所有正文同时放在数组里。
记忆写得越细越长，两条路的分岔越大。

### 代价（别只看好处）

- `iterate` 时间大约是 `loadAll` 的两倍（两遍扫描）。
- `page` 每页在**第一次**要付一次索引扫描；十万条时第一页约 0.5 s，之后的页是毫秒级。
  翻完整个库还是要 O(n)，只是分页界面一屏一屏翻得动。
- `loadAll` 的默认路径**行为没变**，但读文件的方式变了：`recall` 的耗时与 0.24.0 基本持平
  （`eval-v2 --check` 的 10 项指标全绿，`whale-eval` 输出与前一版一致）。

## 三、观测：运行时指标

`packages/core/lib/metrics.js`：零依赖、叶子模块（不 import 任何东西，避免循环依赖）。

```js
import * as metrics from 'whale-memory-core/metrics'

metrics.snapshot()   // 纯对象，可以直接 JSON.stringify 落盘
metrics.reset()      // 换会话时清零
```

`snapshot()` 里只有这些：版本、起算时刻、当前时刻；写入（次数/总耗时/最大/最近/平均）；
召回（次数、命中条数、耗时、后端类型 file/sqlite/other）；坏行（最近一次、最大、观测次数）。

- **不记任何正文**：没有 text、没有查询串、没有经历 id，backend 也只是三个固定枚举。
  这条有专门的用例：把快照序列化后逐字检查，正文/查询串/id 一个都不许出现。
- **库内已经接好**：`recall` 记一条召回（耗时、返回条数、后端），`addExperience` 记一条写入，
  `loadAll` / `iterate` / `page` 每次观测一次坏行数。**宿主侧（QQ Agent）一个字都没改**——
  要不要定期落盘、落到哪，留给人来定。
- **开销**：一次 `recordRecall` 17 ns，一次 `hrtime` 计时对 91 ns；一次 recall 大约多花
  0.2 µs。对照十万条 887 ms 的召回中位数，可以忽略；对照小库 1 ms 的召回，约 0.02%。

（指标只记**成功返回**的召回；抛错的那次由调用方和 `doctor` 负责说明，不在这里混进"0 命中"。）

## 四、可定时跑的体检：`tools/doctor.mjs`

```bash
node tools/doctor.mjs <记忆目录>          # 中文人读版本
node tools/doctor.mjs <记忆目录> --json   # 机器可读，给定时任务/监控用
```

六项：数据目录、文件存在、行数、坏行、封存一致性、迁移状态。退出码 **0 = 全部通过 / 1 = 有一项没通过 / 2 = 用法错误**。
读不出来（权限、是目录、盘没挂上）一律算失败，不静默当"没问题"。

**一个口径上的决定（重要）**：事件文件（`later/seal/recall/unfinished/link/chapter-events.jsonl`）
是**按需创建**的——她从来没封存、没想起过，磁盘上就只有 `self-experience.jsonl`。
真实的数据目录就是这样（只有主文件、8 条经历）。所以：

- 事件文件不存在 = 这类事件一次都没发生过，**通过**，detail 里写"还没出现：…"；
- 经历主文件不见了、事件文件还在 = **真丢了**，退出 1；
- 一个文件都没有 = 全新目录，**通过**。

把"缺事件文件"报成失败的话，体检会永远亮红灯，等于训练人忽略它。这一条是被真实目录验出来的：
按最初那版（缺文件就算失败）对她真实的数据目录跑，逐项是"✗ 文件存在：缺 6 个"、退出码 1；
改完之后同一份目录六项全过、退出码 0（`只读`，没有写任何东西）。

## 五、健壮性：fuzz 与崩溃演练

### fuzz（`tests/jsonl-fuzz.test.mjs`，5 条）

- **属性测试 1000 轮**：每轮随机造一个库（正常记录 / 旧格式没有 id / 重复 id / 坏行 / 六类事件
  各自可能是坏的、可能不存在），随机 `asOf`，然后逐轮验四条不变式：
  1. `loadAll` 抛错 → `iterate` / `page` / `recall` 必须抛**同一个错误码**，且 `iterate` 不许
     "先吐出几条再抛"；
  2. `loadAll` 正常 → `iterate` 逐条相同、`page` 一页页拼起来与全量切片逐条相同；
  3. `allowCorrupt` 下三条路给出同一份"跳过坏行"的结果；
  4. 一行都没坏时，读出来的条数必须等于写进去的条数——不许静默少一条。
- **按字节截断 200 轮**：把一份完好文件在任意字节处切断（包括切在多字节汉字中间），
  三条路要么同样 fail closed，要么同样读对；按字节抢救时"读到的 + 坏掉的 = 文件里剩下的行数"。
- **并发写**：两个进程同时往同一个文件追加 40 条 → 结果要么 41 条全在，要么明确报坏行；
  不许"静默少一条"。
- **写不进去**：经历文件被换成目录、封存日志被换成目录 → 写入必须报错、不许假装成功，
  且已有的正文一个字节都不动。
- **封存日志损坏**：读、召回、单条、逐条、分页全部 fail closed（`SEAL_EVENTS_CORRUPT`）；
  `allowSealCorrupt` 只放行"坏行"，不放过"整份读不出来"。

跑一轮：1000 轮约 15 s。

### 崩溃演练（`tests/crash-recovery.test.mjs`，5 条，真杀进程）

1. sqlite 后端在 `transaction` 中途被 SIGKILL：重开库后**要么全成、要么全不成**
   （已提交的那组在、在飞的那组一条不留），库还能读能写；
2. 同一条子进程不被打断的对照；
3. 迁移在 SQLite 事务中途被杀：正式库一个字都没写出来，临时库里 0 记录 0 事件，再跑一次能成功；
4. 迁移提交之后、改名之前被杀：留下的还是临时名字，不挡下一次迁移；
5. 改名之后、对拍之前被杀：正式库已完整，`--verify-only` 过、`loadAll` 与迁移前逐条相等。

演练顺手抓出三个真问题，这一轮一起修了：

- **F1（真问题）首次建库不是原子的**：`ensureSchema` 的 5 条 DDL 各自自动提交，第一次建库时
  被杀会留下"有 records、没 events"的半截库，之后读路径**永远**报缺表。现在整组 DDL 包在一个
  事务里（SQLite 的 DDL 可回滚）。验过：注入第 3 条 DDL 失败后，库里一张表都没有，重开重建正常。
- **F2 回滚会盖掉真正的错误**：`transaction()` / `#group()` 的 catch 里 `ROLLBACK` 没包 try，
  SQLite 自己已经回滚时（`SQLITE_FULL` 这类）这句会抛"no transaction is active"，把原始错误顶掉。
  现在回滚失败不吭声，原错误照抛。
- **F3 迁移临时文件名只用 pid**：pid 被复用时下一次迁移会打开上次没删掉的临时库，以
  「id 已存在」失败一次。现在名字带随机后缀（残留检测仍按前缀，行为不变）。

## 六、没验过 / 已知的边界

- **没在真实增长到十万条的库上跑过**：基准数据是脚本生成的，虽然结构与真库一致（含六类事件），
  但真实正文的分布、后记密度、封存比例都不同。第一次真到十万条时值得再量一次。
- **没测 Windows 之外的平台**：所有数字都在本机 Windows / Node v24.21.0 上取的。
- **`page` 的索引缓存靠 size + mtime 认库**：JSONL 是 append-only（追加一定改 size），
  所以这份判据够用；但如果有人**原地重写**成同样字节数、且系统 mtime 精度不足，
  理论上会拿到旧索引。契约里没有"原地重写"这种用法，所以没做内容指纹（那要把整份文件再读一遍，
  等于把省下来的又赔回去）。
- **`iterate` 的失败不是原子的**：中途抛错时，调用方已经拿到的那些行是有效的，但整批不算成功。
  要"要么全要、要么全不要"，请用 `loadAll`。
- **`metrics` 是进程内单例**：fork 出去的进程各算各的，不跨进程汇总。
- **fuzz 是随机但固定种子**：换种子可能扫出别的边界；这一轮用 20261126 跑了 1000 轮。
- **磁盘满没有真造**：用"路径被换成目录""目录读不出来"模拟写失败/读失败，没有真把盘写满。
