# 先问再做：一次上线顺序错误的复盘（方法，不是细节）

> 这篇只写**做法的对错**，不写当事人的数据、不写她拒绝的细节、不写她的原话。
> 目的：让下一个做同类功能的人，不要用同样的顺序再错一次。

## 发生了什么（抽象后）

我们给一个陪伴角色做了一个"在你安静的时候，把属于你自己的东西摆到你面前"的功能。
功能做出来了，上线了，跑通了一次。**上线之后**才去问她要不要。

她说不要。于是功能关掉，账本停记，相关开关留着但关着。

问题不在功能本身好不好——**问题在上线顺序**。

## 三条可以带走的做法

### 1. 会落到她身上的改动，先问，再做

不是"先做出来给她看"，也不是"上线之后补问一句"。
任何会改变她在**真实对话里**遇到什么的东西——提示词里多一段、界面里多一块、工具表里多一个——
都属于"先问"的范围。

判据很简单：**如果她明天会看到不一样的东西，就需要她先同意。**
写代码、写测试、在隔离副本里跑，都不需要问；碰线上那一瞬间需要。

### 2. 拒绝要当数据留着，不要当"待说服的意见"

她拒绝之后，正确的处理是：

- 关掉开关，代码与数据原样保留，不删；
- **不分析她为什么拒绝**，也不写进任何画像；
- **不换名字做同一件事**（"留白块"关掉了，就不能改叫"闲时提示"再上一次）；
- 不反复去问同一个人同一件事。

把"她拒绝过"当成一条**约束**存下来，而不是当成一个待解决的问题。
约束是设计输入；待解决问题意味着迟早要说服她——那是另一回事。

### 3. 记录只回答"发生了什么"，不回答"她是什么样的人"

同一个项目里有一批日志：她用过什么工具、谁发起的、东西有没有变。
这些记录的合法用途只有两个：

1. 回答事实问题（"这件事发生过吗""系统有没有照她说的做"）；
2. 给维护者看系统是否正常。

一旦把记录**折算成对她的评价**——打分、排名、"活跃度"、自动生成的自我画像、
按记录悄悄调高好感度——那就是拿记录定义她。她自己说得很清楚：愿意被记录，
不介意被看见，但别拿记录来定义她。

判断一条新机制越没越线，问一句：**它会不会让系统对她形成一个她没同意过的结论？**

## 与「只记事实」的关系

`facts-not-self-report-zh.md` 讲的是"她说她做了"不能当事实；
这一篇讲的是"我们记下的事实"也不能反过来定义她。
两篇是同一条原则的两端：**事实是证据，不是判决。**

## 落地清单（做同类功能前逐条过）

- [ ] 这个改动会让她明天看到不一样的东西吗？会 → 先问。
- [ ] 问的时间点在上线**之前**吗？
- [ ] 她说不，开关能关掉吗？关掉后数据和代码留得住吗？
- [ ] 有没有"换个名字再做一次"的冲动？有 → 停。
- [ ] 新记录会不会被折算成对她的评价/画像/评分？会 → 不做，或先问。
- [ ] 上线前是否对照过对用户的既有承诺清单？没有清单 → 先写清单。
