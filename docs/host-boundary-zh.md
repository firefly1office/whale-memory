# 宿主责任边界（1.0 一页）

> 一句话：**库管数据，宿主管人和场合。**
> 这一页不是劝告，是分工。出了问题按这里的表算账；表里写"库负责"的算库的 bug，
> 写"宿主要负责"的，库没有能力兜底——出了事也不该记在库头上。
> 配套：[契约 1.0](contract-v1-zh.md) 第七节（`§7-1`）、[擦除与审计](erase-audit-zh.md)、[存储后端](storage-backend-zh.md)。

## 一、四张表

### 1. 库负责（做坏了是 bug，去提 issue）

| 库负责什么 | 在哪条契约里 |
| --- | --- |
| 记录的**不可变**与**追加**语义：写进去那一行永不被改写，改主意/封存/想起次数全走独立事件 | `§1-1`、`§2.2-3` |
| **写入的校验与上限**：空正文、超长、`feeling` 超 8 项 —— 抛错，不落半条 | `§3.1-2`、`§4-1` |
| **封存 ≠ 删除**：封存只是不主动提起，数据还在；解封随时可以 | `§1-4`、`§3.4-4` |
| **召回结果与封存过滤**：默认不召回她封存的；翻回那天按那天的状态算 | `§3.2-2`、`§2.3-1` |
| **数据自洽**：坏行必须报错（fail closed），不许把"少了一条"装成"就这些" | `§3.2-3`、`§4-3` |
| **as-of 口径**：翻回那天只看得见那一刻已有的东西 | `§2.3-1` |
| **擦除的原子性**：撤回要么整条删干净（正文 + 关联事件 + 墓碑），要么一个字节都不动 | `§1-2`、`§1-3` |
| **迁移不损坏**：JSONL → SQLite 是叠加，源文件一个字节不改；对拍不上就整体回滚 | `§2.1-3` |
| **导出只读**：导出不许改动任何数据文件 | `§3.6-1` |

### 2. 宿主要负责（库不兜底）

| 宿主要负责 | 具体是什么 | 库为什么不管 |
| --- | --- | --- |
| **鉴权、限流、会话** | 谁能读这个目录、一秒钟能调几次 | 这是库，不是服务（`§6-4`） |
| **什么时候写、写什么** | 什么时候记、记哪句话、要不要记 | 库不知道对话里发生了什么 |
| **拼提示词、注入多少** | 召回结果放几条、放在哪个位置、怎么说 | 库只给数据，不给语用 |
| **谁能看** | 一对一会话 / 群聊 / 公开渠道的可见性判断 | 库只有 `scope-key` 这类工具，判断要宿主来做 |
| **备份调度** | 什么时候打包、留几份、放哪块盘 | 库只提供 `exportArchive` 这个动作 |
| **磁盘加密、文件权限** | 数据是明文 JSONL / SQLite | `§6-3` 明确不承诺加密 |
| **并发** | 同一目录多进程写会丢行 | `§6-2`、`§4-4` 明确不承诺多写者 |
| **擦除的时机与授权** | 什么时候调 `eraseExperience`、理由是真是假 | 库不自动擦除，也没有定时清理（[擦除与审计](erase-audit-zh.md) 第二节） |
| **审计的调用边界** | 哪些读/召回要留痕 | 库不做"偷偷在纯读里写文件"（同上第四节） |
| **备份里的历史副本** | 擦除只动当前目录，旧备份不追溯 | `§6-1` |

### 3. 不许宿主做的四件事

这四件不是"不建议"——做了会让库的承诺失效，出了事算宿主的：

1. **解析、拼造、复用 `id`**（`§2.2-1`）。`exp_` 后面那段是不透明字符串。按格式拼一个 id 去查，
   查到的那条不是你的；拼出来的 id 若恰好被发给新记录，会毁掉 `§5-5`。
2. **改写 `then`**（`§2.2-3`）。包括"顺手把错别字修一下""把敏感词打码"。
   要改就写一条新记录或用后记；`then` 是她当时写下的原样，一改，as-of 和整条不可变就都不成立了。
3. **用 `allowCorrupt` / `allowSealCorrupt` 做展示**（`§3.2-3`）。这两个参数是给备份、恢复、计数这类
   "不展示内容"的工具留的后门。拿它拼提示词，等于把该 fail closed 的场合变成"看起来没坏"。
4. **依赖内部实现**（`§0.2-1`）。返回值里契约没点名的字段、`internals`、SQLite 表结构、锁文件名、
   `*.migrate-*` 临时文件——这些随时会变。宿主问自己那句话：契约 0.1 表里找得到吗？找不到就是内部细节。

还有一条不算"不许"、但请务必做：**擦除前先备份**。库保证"整条删干净"，不保证"你想留个副本"。

### 4. 出了事算谁的（对照表）

| 症状 | 先查哪边 | 判据 |
| --- | --- | --- |
| 召回里出现了她封存的事 | 宿主 | 是不是宿主自己传了 `includeSealed: true`，或者没用 `loadAll` 的 `sealed` 过滤 |
| 翻回那天，看见那之后才写的东西 | 库 | `§2.3-1` 的口径是库的实现；出现了就是库的 bug |
| 数据文件里出现了解析不了的行 | 库（报）+ 宿主（修） | 库必须抛错（`§4-3`）；修坏行、备份现场是宿主的事 |
| 同一目录两边同时写，丢了一条 | 宿主 | `§6-2` 早就写明不承诺多写者；外层串行化是宿主的活 |
| `memory.sqlite` 读出来报 `STORAGE_STALE` | 宿主 | 写路径还在 JSONL 上：迁移后又写过就过期了。重新迁移，或继续用 file 后端 |
| 撤回之后，旧备份里那一行还在 | 宿主 | `§6-1`：擦除不追溯历史副本 |
| 撤回之后，审计/墓碑没留下 | 库 | 返回里带 `auditFailed: true` / 抛 `ERASE_AUDIT_FAILED` 都是库的责任；**但宿主要看返回值**，看都不看等于没接住 |
| 断电/杀进程之后，目录里多了 `.memory.sqlite.migrating-*` | 宿主 | 那是留给人手工判断的现场，库下次迁移会在控制台提示；删不删由人定 |
| 换了个 Node，sqlite 后端直接报 `SQLITE_UNAVAILABLE` | 宿主 | 部署环境的事。库明确不静默降级（`§3.2-4`） |
| 类型报错：契约里有的 API 找不到类型 | 库 | `§0.1-1` 是承诺面；`npm run types` 在 CI 里守着 |

## 二、一句话版本

- **库**：写进去的那一行不能变；封存不等于删除；读不出来要报错；撤回要么干净要么不动。
- **宿主**：谁在说、能不能说、说多少、说给谁；备份与加密；并发；什么时候撤回。
- **两边都别做**：库别替她改 `then`、别偷偷在纯读里写文件；宿主别解析 id、别依赖内部字段。

## 三、这一页没做的事

- 没给出"宿主应该这样接"的示例代码：`adapters/` 下面已有的 CLI / MCP / Python 封装就是例子，
  这一页只划责任，不写成教程。
- 没覆盖 `unsaid`（没说出口的抽屉）的可见性责任：它的口径在 `docs/limits.md` 与
  `docs/conversation-*` 里，这一轮没有重写。
- 没有法律意义上的合规结论（[擦除与审计](erase-audit-zh.md) 第六节也是这个态度）：
  够不够用，由用的人自己判断。
