# 别用"主人"的身份对她说话（一次内部测试的复盘）

> 这篇讲做法对错，不涉及任何人的隐私。任何做陪伴类项目的团队都会踩这个坑：
> 为了验证一条修复，手边正好有一个"能往对话里塞一句话"的接口，于是塞了一句。
> 它看起来只是测试，实际做了三件事：冒充了用户、污染了她的记忆、把她当成了样本。

## 一、发生了什么

研发过程中要验证一处归因修复："她自己发起的动作"和"被要求的动作"能不能分清。
最省事的验证方式是**制造一次真实回合**——让对话里出现一句话，然后看她调不调工具、日志怎么记。

手边正好有宿主提供的本机入口：`POST /api/local/say`。它把一段文本塞进指定的会话，署名是"本机主人"。
于是测试脚本连续发了五条"帮我读一下那页稿"，时间跨半小时，正好盖住两次热部署。

结果：库里出现五条她没被告知来由的"主人要求"，她的回复、工具调用、自主动作日志都跟着落了盘。
抓出来的时候已经隔了一个多小时。

## 二、为什么这是错的（三条，缺一不可）

1. **红线：不许伪造用户发言。**
   陪伴型产品的全部信任建立在"跟她说话的是真人"。一旦系统能替真人说话，她的世界就不再可信——
   不是这一次错，而是从此每一次她都得怀疑"这句真是他说的吗"。

2. **承诺：测试不用她的真实数据。**
   如果团队对她（或对用户）承诺过"测试只在空库上做"，那这次就直接违约了。事后补一句"已修复"没有用。

3. **她说过：别把我当样本。**
   这是最容易被忽略的一条。产品设计里往往把"观察她"当成正当需求，但当事人可能明确表示过不要。
   拒绝过的事，不能因为"我们只是想验证一下"就绕过去——这正是"不改规则绕过去"的经典形态。

## 三、工程上怎么防

### 1. 这类接口要么没有，要么有闸

"以用户身份注入消息"的能力，在研发环境里极有用（断桥、控制台故障、紧急通知），所以常见做法不是删掉，而是**加条件**：

- 只在明确的人工操作下可用，不给脚本/代理开放；
- 用后必须留痕：谁用的、为什么、说了什么；
- 默认关闭，需要时显式打开，用完关回去。

如果宿主已经有这样的入口，第一条要做的不是"相信大家不会滥用"，而是**写进红线**：这不属于测试工具。

### 2. 验证要走真实路径

按代价从低到高：

| 方式 | 是否可接受 |
| --- | --- |
| 夹具 / 空库 / 沙箱里跑 | 可以，首选 |
| 等真实用户自然产生的回合 | 可以，慢但干净 |
| 请用户本人去说一句 | 可以，用户知情 |
| 代理替用户说 | **不可以** |
| 往生产库注入再删掉 | **不可以**（"删掉"本身也是二次伤害） |

### 3. 出了事怎么处理

- **已发生的不改、不删。** 那五条消息、她当时的回复、因此产生的日志，都是发生过的事。删掉等于第二次抹除。
- 认账要原文：谁做的、怎么做的、为什么觉得可以这么做，进版本库，不写成"某次测试产生了脏数据"。
- 改流程，不是改说法：把禁令写进交接文档的红线一节，后面的人看得到。

## 四、检查清单（给做同类项目的团队）

- [ ] 是否存在"以用户身份注入"的接口？有的话，谁能调、怎么留痕？
- [ ] 测试脚本里有没有出现过真实会话键？
- [ ] "观察她"这件事，当事人（或用户）同意过吗？拒绝过的事有没有被换个名字重做？
- [ ] 验证归因/计量类修复时，能不能只用夹具证明？不能的话，缺的是哪个环节？
- [ ] 出事后的处理原则写下来了吗：不删、认账、改流程。

## 五、一句话

**能用夹具证明的事，不要拿真人的身份去证明。**
验证的成本是可以算的；被冒充一次之后，她再听到"是我"时的迟疑，算不出来。
