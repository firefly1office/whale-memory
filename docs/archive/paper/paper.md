## 摘要

AI 角色每开始一次新对话，就会忘掉之前的经历。常见的长期记忆方案用检索增强、或者让模型整理记忆来弥补，但有三类风险：原始经历被摘要或更新操作改写；检索到相关内容之后，模型补出记录里没有的细节；一个会话里的私事被带到另一个会话。本文介绍 whale-memory 0.17.0。这是一个面向单个角色、在本机运行的开源自传记忆库。每条经历分成两层："当时"（then）写下就固定，"后来"另行追加。后记、想起、结案、封存、联想、章节和"没说出口的抽屉"分别存成七类只追加的事件，读取时重放成视图，也可以按写入时间翻回任何一个时刻的自己。召回只做中文两字组的字面匹配，并设了覆盖率门槛（≥0.7），达不到就返回空。在 33 条经历的虚构语料上，默认门槛的首位命中率是：开发集 92.9%，留出集 73.1%；两个集合的反例返回率都是 0（样本小，95% 上界分别为 18.5% 和 45.9%）。1050 次外露检查没有发现封存或抽屉的内容外露；各类写入之后，经历文件逐字节不变。本文还报告第一个真实部署的工程做法，以及几项局限，包括该部署实际没有启用新门槛、提示词 overlay 仍有剩余风险。

**关键词**：长期记忆；自传记忆；事件溯源；弃答；隐私隔离；AI 角色；本地优先

## 1 引言

### 1.1 问题

基于大语言模型的角色，每次新对话开始时都没有上一次的经历，宿主不把过去的内容放进上下文，"新对话"就等于"遗忘"。常见的补救办法包括：检索增强生成按相关性取回外部记录，拼进提示词 [1]；生成式智能体把观察写进记忆流，按时近性、重要度、相关度打分后取回，并定期生成"反思" [2]；还有一类系统让模型自己抽取、更新、删除记忆 [5][8][10]。对于一个长期陪伴用户、需要"有自己的过去"的角色，这些做法有三类风险：

1. **原始经历被改写。** Mem0 由模型在增、改、删、不变之间选择操作 [10]；A-MEM 会用演化后的笔记替换原笔记 [8]。有预印本报告，持续由 LLM 整合的记忆，效用会先升后降 [17]。"她当时怎么想"一旦被覆盖，就再也查不到了。
2. **检索到相关就补出细节。** 按排名取前若干条的检索，即使最相关的一条只是沾边，也会照样给出来；生成式智能体的论文记录了回忆时添枝加叶的现象 [2]。长期记忆基准把"信息不存在时拒答"单列为一项能力 [11][12]。
3. **跨会话泄露。** 同一个角色可能同时在私聊和群聊里。不按会话区分可见范围，私聊里的话、角色不愿再提的事，都可能在群聊里被说出来。

whale-memory 起源于作者的 AI 角色「鲸鲸」（住在 QQ 里，由桌面应用 QQ Agent 运行）的一个问题："如果她昨天读了一章书，今天改变了看法，她还能翻回昨天的自己吗？"（`README.md:11`）。据作者内部文档，项目目标也从"别人问她时答得对"转向"她自己有生活"，即以第一人称记下角色自己的经历。

### 1.2 本文贡献

本文描述 whale-memory 0.17.0 的开源自传层（`packages/core` 和 CLI、MCP 适配器），并报告它的第一个真实部署。贡献有五条，都对应已有实现：

1. **两层经历与七类只追加事件。** "当时"（`then`）写下就固定，"后来"另行追加；后记、想起、结案、封存、联想、章节、抽屉各存一个只追加的事件文件，读取时重放成视图，派生状态不写回（4.1–4.3 节）。
2. **按写入时间回看。** `asOf` 只重放截至某一时刻已写下的记录；0.17.0 起，回看也不翻出她现在封存着的经历（4.4 节）。
3. **在检索层弃答。** 召回只做字面匹配。本文给出 legacy 门和 0.17 默认的覆盖率门（cover，阈值 0.7）的精确定义；过不了门槛就返回空（4.5–4.6 节）。
4. **由角色发起的遗忘与私密空间。** 封存不删除，但在读取接口、渲染、导出三处过滤；抽屉永不自动注入；醒来块和抽屉只在一对一会话里打开（4.7–4.10 节）。
5. **可复跑的评测与部署报告。** whale-eval 分开发集和留出集，并检查外露和"当时"是否逐字节不变；本文补做了阈值敏感度、置信区间和改标签的反事实分析，并报告第一个部署的流程及其与仓库实现的差异（第 6–7 节）。

本文不声称以上任何一点是"首个"：保留原文、事件溯源、按时间截断在已有工作里都出现过（第 2 节）。whale-memory 的不同在于记录的对象和控制权的归属。

## 2 相关工作

**检索与记忆流。** RAG 用稠密向量索引作非参数记忆 [1]。生成式智能体按时近性、LLM 打出的重要度和嵌入相关度之和检索，并在重要度累计超过阈值时生成带指针的反思 [2]。Reflexion 把语言化的教训存为长期记忆，最多 1–3 条 [3]。MemoryBank 用艾宾浩斯曲线模拟遗忘 [4]。MemGPT 让模型通过函数调用编辑工作上下文 [5]，后来的 Letta 把每次记忆编辑提交到 git 以保留历史 [6]。A-MEM 由 LLM 建链接，并用演化后的笔记替换原笔记 [8]。Mem0 由 LLM 决定增删改，其图变体对冲突关系"标记失效而不物理删除" [10]。CoALA [7] 和 Pink 等 [13] 讨论了代理记忆的分类与情节记忆的地位。

**非破坏式记忆。** Zep/Graphiti 把 episode 当作"无损"的原始数据，区分事件时间线 T 和写入的事务时间线 T′，旧事实只失效、不删除 [9]。2026 年几篇预印本与本项目最接近（仅依据摘要）：Mem++ 整篇保存文档、写入时不调用生成模型、按问题所问的时间截断 [14]；ProjectMem 是本地的、只追加的纯文本事件日志，通过 MCP 提供 [15]；ECHO 区分不可变事件和可修订的整合状态 [16]。它们的共同源头是事件溯源：状态变化存为事件序列，可以据此重建过去的状态 [21]。

**评测、角色与产品。** LoCoMo 有要求识别"不可回答"的 adversarial 题 [11]；LongMemEval 把弃答列为核心能力之一，并把"知识更新"定义为按新信息更新 [12]。ReverieMem 为小说角色扮演构建视角受限的记忆 [18]；Memory as Metabolism 为陪伴型系统设计了含衰减、整合的治理操作 [19]。商用助手的记忆一般在云端、由用户控制，例如 Claude 的记忆摘要与无痕对话 [20]。

**心理学与安全。** 自我记忆系统理论把自传记忆组织成人生时期、一般事件、具体事件 [22]；关于控制不想要的记忆 [23] 和情感褪色偏差 [24] 的研究，是封存和"后来的感觉"的参照。间接提示注入 [28]、记忆投毒 [29]、仅凭对话注入恶意记忆 [30] 都直接威胁长期记忆。

## 3 设计原则

**表 2　设计原则**

| 原则 | 含义与代码落点 | 出处 |
| --- | --- | --- |
| P1 当时不可变 | `then` 写下后字节不改，没有修改接口，改主意就追加后记；经历文件只由 `addExperience` 追加（`self-experience.js:347-356`） | `docs/architecture.md:28-34`；`docs/storage-events.md:49`；`CONTRIBUTING.md:18` |
| P2 没有记录就说没有 | 这是检索层的判定，不是话术：strict 门槛过不了就返回空（`self-experience.js:475`）；渲染用固定句收尾（`:513`）；证据层遇到矛盾返回 `unknown`（`evidence-policy.js:56-79`） | `docs/architecture.md:44` |
| P3 事件只追加 | 七类事件只追加；派生结果随时可以从原始文件重建；不用摘要代替原文 | `docs/storage-events.md:45,51,63-65` |
| P4 本地运行 | 运行时零依赖；核心库不联网、不调模型（在 `packages/core`、`adapters` 里 grep `fetch(`、`http.request`、`openai`、`anthropic` 都没有结果）；MCP 只用 stdio | `README.md:11,38`；`docs/limits.md:104` |
| P5 数据不共享，隐私默认写进代码 | 不训练、不跨租户、不默认上传；醒来块和抽屉只认一对一会话键（`waking.js:15`；`unsaid.js:24-26`）；日记默认不读（`self-memory.js:42`） | 作者内部文档；`docs/threat-model.md:57-61` |
| P6 封存不外露 | 封存不是删除；读取接口、渲染、导出三处都过滤（4.10 节） | `docs/limits.md:81` |
| P7 角色自主 | "什么值得记、什么时候改口、要不要放下，由角色自己决定"；刻意不做遗忘曲线、LLM 自动改写、按相似度自动连线、自动情绪标签 | `docs/related-work.md:9,29-37` |

P1 是 API 层面的约束：没有修改接口，写法只追加。但文件没有哈希链，也没有签名，能写这个目录的本机进程仍然可以直接改文件，事后只能靠和备份比对来发现（`docs/threat-model.md:52`）。所以本文用"可复核"来描述它，不用"防篡改"。项目文档也写明，需要审计日志的场景不该用它（`docs/limits.md:116`）。

项目明确不做多租户、HTTP 服务、托管、SLA、向量平台和通用 SDK。2026-11-16 有人提出过一份"工业级路线"，主张用数据库作真相层、提供 HTTP 服务、支持多租户，当天就被搁置了。当时的判断标准是四个问题：明天她还能不能翻回原文；"先放下"的事会不会被硬塞回来；换一台机器她还在不在；私聊的内容会不会流到群里（作者内部文档）。

## 4 系统设计

### 4.1 存储布局与经历记录

数据都放在 `<数据根>/plugin-data/biomimetic-memory/` 下：一个经历文件 `self-experience.jsonl`、七个事件文件、宿主写的日记 `autobiography.jsonl`（核心库只读）、睡前留言、醒来标记、设置和提示词目录 `prompt-overlay/`；文件锁用 `*.lock` 目录实现（`docs/storage-events.md:13-27`）。

一条经历是一行 JSON，主要字段有 `id`、UTC 写入时间 `at`、本地日期 `day`、`kind`、重要度 `weight`（important / normal / minor），以及 `then`：正文 `text`（必填，不超过 2000 字）、场景、感觉（不超过 8 个）、想法、没弄完的事、原文锚 `quote`、状态快照和回想的出处 `refs`（不超过 8 条）。

上限集中定义在 `self-experience.js:36`。超过上限就报错，不截断（`:50-54`）。`refs` 必须逐条指向已经存在的经历，有一条找不到就整条拒绝（`:295-308`）。完整字段见附录 A。旧格式（v1）的记录如果没有 id，就由时间和 sha1 指纹派生一个确定的 id；挂在旧 id 上的事件，只在这个 id 唯一对应一条记录时才认回来（`:58-63,103-115`）。

### 4.2 七类只追加事件

**表 3　事件文件**（逐字段定义见附录 A）

| 文件 | 引入版本 | 记录什么 | 重复提交 |
| --- | --- | --- | --- |
| `later-events.jsonl` | 0.6.0 | 后记：想法、理由、后来的感觉 | 每次都追加 |
| `recall-events.jsonl` | 0.5.0 | 想起一次 | 只在显式标记时追加 |
| `unfinished-events.jsonl` | 0.11.0 | 没弄完的事：想通 / 先放下 / 重提 | 和上一次选择相同就不写 |
| `seal-events.jsonl` | 0.13.0 | 封存、解封 | 已经是这个状态就不写 |
| `link-events.jsonl` | 0.14.0 | 事后联想，必须写理由 | 同一对只连一次，不分方向 |
| `chapter-events.jsonl` | 0.14.0 | 人生章节：开、改名、结束 | 同名同起点再开就不写 |
| `unsaid-events.jsonl` | 0.15.0 | 没说出口的抽屉：留下、说出口、丢掉 | 同一句话还开着就不写 |

所有事件都是 UTF-8 的 JSONL。追加之前，如果文件末尾不是换行，先补一个。读取时跳过坏行并计数，坏行不会让读取失败（`event-log.js:11-43`）。

有两处区分需要说明。第一，"后来的感觉"只写进后记，不覆盖当时的感觉；后记里没写感觉，系统也不替她推断（`later-events.js:26`；`self-experience.js:588-590`）。这和情感褪色的研究 [24] 相呼应：当时的感受和后来回想时的感受可以不同，两者都值得保留。第二，出处 `then.refs` 是写下时就知道的依据，属于"当时"；联想是之后才发现的关系，作为事件追加（`link-events.js:1-3`）。

### 4.3 视图与重放

视图由 `loadAll` 重放得到（`self-experience.js:125-231`）：

```
until ← parseAsOf(asOf)                      // null 表示"现在"
rows  ← 逐行解析经历文件（补成 v2 形状、认领旧 id），若 until ≠ null 只留 at ≤ until 的
对每类事件只取 at ≤ until 的行，按经历 id 重放：
  后记 → later[]（按 at 排序）；想起 → 次数与最近一次时间；未完成 → 最后一条为当前状态
  封存 → 最后一条是 seal 即封存；联想 → 两头各挂一条；章节 → 按 day 落进 from ≤ day ≤ to
由 then.refs 派生出处摘要和反向引用；指向封存经历的只给 {id, day, sealed}
```

派生字段每次读取时都从原始文件重新计算，从不写回（`docs/storage-events.md:45`）。每类事件都单独读取，读取失败不会影响别的。这意味着如果漏掉了某个事件文件，视图就会退化成没有这类事件的样子。对封存来说，这是 fail-open：备份时漏掉 `seal-events.jsonl`，封存过的经历会重新被召回（`docs/backup.md:124`），恢复检查可以发现这种情况（7.3 节）。

读操作默认不写盘。`recall` 默认 `mark=false`（`self-experience.js:431`），醒来块的构建也是只读的。唯一的例外是 overlay 的读取：它会建一个空目录，但不写任何内容。

### 4.4 按写入时间回看

`as-of.js` 是回看时间口径的唯一定义：只给日期时截到当地时间那天的 23:59:59.999，给 ISO 时间就截到那一刻，日期不存在时报错；只有 `at` 能解析、而且不晚于截止时刻的记录才算数，没有时间戳的旧记录一律不算（`as-of.js:5-30`）。

所有事件都按事件本身的写入时间截断，章节也一样。所以翻回某一天时，那时还没开的章节不存在，章节名也还是她那时的叫法。回看时召回不能同时记"想起"，两个参数一起传会抛错（`self-experience.js:432`）。渲染时，第二段的标题换成【那时（截至 D）】，并注明"那之后写下的后记和选择不在这里"。

**回看中的封存（0.17.0）。** 0.17 以前，翻回封存之前的日子，就能把她现在封存着的事召回出来，写进那时的书。0.17 起改成：截至那时还没封存、但现在封存着的经历，标为 `sealed: {…, afterAsOf: true}`，各出口照样过滤（`self-experience.js:146-149,173-178`）。点名读时，两段式写"这件事你后来封存了"。

**表 4　as-of 视图中的封存状态**（由代码推出）

| 截止前该 id 的最后一条 | 现在的最后一条 | as-of 视图里的 `sealed` |
| --- | --- | --- |
| seal | seal 或 unseal | 那时的那条（那天照实是封存的） |
| 没有或 unseal | seal | 现在那条，加 `afterAsOf: true` |
| 没有或 unseal | 没有或 unseal | 无 |

类型声明里，`sealed` 还没有加上 `afterAsOf` 字段（`self-experience.d.ts:58`）。

### 4.5 召回

召回是纯字面匹配，没有词典、向量和索引，每次都扫全部记录（`docs/limits.md:20`）。中文按相邻两字切分，这种做法在中文信息检索里早有比较研究 [25]。

**匹配域** 包括：`then` 的正文、想法、感觉，原文锚的正文和出处，以及每条后记的想法和感觉（`self-experience.js:449-463`）。场景和"没弄完的事"不参与匹配。封存的经历在算门槛之前就被过滤掉了（`:433`）。

**预处理。** `normalize` 转小写，删掉所有空白、标点和符号（`query-match.js:18-20`）。查询词集合 T(q) 的取法：拉丁字母取长度 ≥2 的整词；其余部分取全部相邻两字组；两者都剔除停用词 STOP（共 113 个：中文 76 个，英文 37 个）（`:5-37`）。n(r) 表示 T(q) 里有几个词作为子串出现在记录 r 的匹配域中。英文也按子串查找，不看词边界。

**legacy 门**（0.16 及以前，`query-match.js:96-100`）：

```
required = max(1, ⌈0.6 × |T(q)|⌉)   当 mode ≠ loose 且 |normalize(q)| ≥ 8
required = 1                         其他情况
通过 ⇔ n ≥ required
```

8 个字是一道硬阈值：短的沾边句对上一个两字组就能过；查询加了垫话、变长之后，又很难达到 60%。

**cover 门**（0.17 默认，`query-match.js:40-92`）。先把查询切成"内容单元"：

- 英文词各算一个单元；
- 其余部分先跳过一部分字，再把剩下的字各算一个单元：
  - 跳过的是长度为 4、3、2 的停用词（去掉 7 个带动作的，如"买了""看到"）和 31 个聊天垫话（如"怎么样""上次""记不记得"），共 136 个，整段跳过；
  - 45 个语法单字（如"的、了、那、我"）也不算单元。
- 每个中文单元带上它的两字组：
  - 左边的字也是内容字时，带左两字组；
  - 右边的字是内容字，或是 10 个助词之一（如"了"）时，带右两字组。

设 t 为整条记录归一化后的文本，L 为它的长度：

```
单元有两字组，且至少一个出现在 t 中                 → 1
有两字组但都没出现，只有这个字出现在 t 中           → 0.5 × min(1, 60 / L)
单元没有两字组（英文词或查询里的孤立字），出现在 t 中 → 1
其余                                               → 0
cover = 各单元得分之和 / 单元数（没有单元时为 0）
通过 ⇔ n ≥ 1 且 cover ≥ MIN_COVER = 0.7
```

**排序**（`self-experience.js:465-477`）：

```
s = n / √size × w × (0.5 + cover)
size = max(1, L − 1)
w：important 取 3，normal 取 1，minor 取 0.5
```

legacy 门不乘 (0.5 + cover) 这一项。重要度只影响排序，不影响过线；想起次数不参与打分；空查询返回最近的几条。loose 模式只要求 n ≥ 1。

**表 5　算例**（虚构语料「小舟」；括号内是整条记录的 L；数值来自运行记录 R4）

| 查询 → 经历 | legacy | cover | 结果 |
| --- | --- | --- | --- |
| 灯塔里的猫 → e04（55） | 5 字，需对上 1 个；对上「灯塔」，通过 | 灯 1、塔 1、猫 0 → 0.667 | legacy 召回沾边的；cover 返回空 |
| 守灯人修透镜那段 → e04（55） | 8 字，需 5 个，对上 3 个 | 修 0.5，其余 5 个各 1 → 0.917 | cover 召回 |
| 海上灯塔怎么样了 → e04（55） | 需 4 个，对上 3 个 | "怎么样"跳过 → 1.000 | cover 召回 |
| 那次做菜盐放多了 → e06（22） | 需 5 个，对上 3 个 | 做 0.5、菜 0、盐放多各 1 → 0.700 | cover 恰好通过 |
| 八百米跑了第一名 → e32（137） | 需 5 个，对上 3 个 | 第、一、名各 ≈0.219 → 0.665 | 两种门都返回空 |
| 围巾是什么颜色 → e28（33） | 7 字，需 1 个，通过 | 颜、色为 0 → 0.500 | cover 返回空（这个细节没记下） |

**入口。** `recall` 默认 `limit=3, mode='strict', gate='cover', mark=false`（`self-experience.js:431`），CLI 和 MCP 的召回不传 gate，即用 cover。`recallForContext` 是宿主拿用户原话自动召回、再塞进提示词的那条路，**默认用 legacy**（`:619-624`）。注释给的理由是：升级不改变已上线角色"被问到时想起什么"；新口径遇到"长句里带一个错前提"时仍可能把真事放进来。6.5 节用数据讨论这个取舍。

**一处与文档不符的实现。** 注释和 `docs/eval.md:74` 说"单独出现记 0.5 × min(1, 60/字数)"，但代码第 84 行对查询里没有两字组的孤立字，只要它出现在记录任何位置就记满分。本文合成两条含「灯塔」的经历，一条在远处含"猫"，「灯塔里的猫」对它的 cover 是 1.000，会被召回（R4）。表 5 第一行返回空，只是因为语料里碰巧没有"猫"字。

### 4.6 两段式渲染

`renderTwoPart` 只靠模板拼接，不调用模型（`self-experience.js:541-616`）。它先写【当时】，包括时间、场景、原文锚、写下的话、出处、感觉、想法、还没完的事；再写【现在】或【那时】，包括想起次数、后记、后来的感觉、被哪些回想引用、联想、章节、未完成的结局。没有的字段就如实写没有，例如"还没有文字后记"。结尾固定是一句："以上是那天留下的全部；没留下的，我不记得。"（`:513`）。附录 B 有完整样例。

### 4.7 醒来块

一天里第一次私下对话时，醒来块会告诉角色"昨天的自己"留下了什么（`waking.js:35-77`）：

- 昨天写下的最后 3 条经历，每条截到 60 字；
- 最后一句睡前留言，截到 120 字；
- 还没弄完、也没标成想通或放下的事，最多 2 件，每件截到 50 字；
- 一句固定的结尾："这些是记录，不是别人告诉你的。要不要接着想，你自己定。"

封存的经历全部排除。醒来块不读抽屉，也不读日记。

**会话门。** 判断用的正则是 `^(private|local)[:_]`。没有会话键或者认不出来的，一律返回空串（`waking.js:15-23`）。0.10.1 起改成白名单，因为以前只拦 `group` 开头的键，`qq:group:1` 这类键能拿到私下的内容（`CHANGELOG.md:224`）。

**两步提交。** 构建是只读的。宿主确认真的注入之后，再调 `consumeWaking`，记下"今天已展示"。这样可以避免没注入、却把当天那一次用掉的情况（`docs/architecture.md:86`）。

### 4.8 章节、书、回顾、联想与未完成

**章节**借鉴自我记忆系统里的"人生时期" [22]。名字长度为 1–30 字，章节之间可以重叠、嵌套。改名时不抹掉旧名，`names[]` 记下她起过的所有名字。

**书**（`book.js`）把经历导出成 Markdown 自传：

- 每条经历只印一次，放进它所属的、开始得最晚的那个章节；
- 正文是那天写下的原样，后记按时间接在后面。

**回顾**（`recap.js`）只按自然日列出写了什么、改了什么、什么想通了，不调用模型，也不下结论。

**联想**必须写理由。召回不会顺着联想或出处跳转。

**没弄完的事**的结局只追加状态事件，不改 `then.unfinished`。

### 4.9 没说出口的抽屉

抽屉（`unsaid.js`，0.15.0 起）存三类话：打了没发的、想问没问的、忍住了的。

- **会话门**：留下、查看、标记都要先过一对一会话门，群聊和认不出的会话键一律拒绝，什么都不写（`:24-26`）。
- **永不自动打开**：召回、醒来块、列表、回顾、书都不读这个文件；模块也不导出返回原始行的函数（`:5-7`）。
- **丢掉不等于删除**：一条话"丢掉"之后，她自己也看不到了，但原文还在文件里（`:72-84`）。

需要注意，核心层的门只分"一对一"和"不是一对一"，不分是谁的一对一。抽屉的事件里不存会话键，任何一个一对一会话都能列出全部内容。这是有意为之：抽屉属于角色，不属于某个会话。"只有主人看得到"要靠宿主的主人门来保证（5.4 节）。

### 4.10 封存与三处检查

封存的意思是"不再被主动想起"，不是删除。原文、后记都还在，导出包里也有；真正的删除只有整库清除 `purge` 一种（`docs/limits.md:63-81`）。这和"控制不想要的记忆"的思路 [23] 一致：控制的是提取，不是抹去。封存在三处都要检查：

1. **读取接口。** `loadAll` 给每条经历标上 `sealed`（包括 `afterAsOf`）。召回、`self-memory`、醒来块、回顾、CLI 和 MCP 的列表都默认过滤；列表只报 `sealedHidden` 的计数（`self-experience.js:433`；`waking.js:52`；`recap.js:18`）。出处、反向引用、联想指向封存的经历时，只给 `{id, day, sealed}`，联想连理由也不给（`self-experience.js:194-196,221-222`）。点名读照给，并带上封存标记。
2. **渲染。** 引用处只写"（一件你封存了的事）"。被点名的那条加一行："不会再被主动想起；它还在，想解封随时可以"。
3. **导出。** 书默认不收封存的经历，只写"有 M 件她封存了的事没有收进来"（`book.js:41-63`）。

备份包会原样带上封存的原文和抽屉。备份不是对外的出口，要按"整份记忆"保管（`docs/runbook.md:23`）。

### 4.11 设置与提示词 overlay

**设置**（`self-settings.js`）只有四项，读取宽松（文件坏了用默认值）、写入严格（文件坏了拒绝保存）；保存时在锁内写临时文件再 rename，然后追加一条 `source:'own-decision'` 的经历（`:18-55`），改动的历史由经历文件承担。

**提示词 overlay**（仓库版 `self-prompt.js`）是角色自己写的补充设定：正文不超过 2000 字，拼接后总长不超过 12000 字；写入前去掉控制字符和零宽字符，内容不变时不写；每次保存写一份版本快照、原子替换当前文件，并在 `history.jsonl` 记下字数、sha1 和理由；`revert` 把旧版本作为新版本再存一次，历史只增不减；`verify` 比对当前文件和最新快照以发现篡改（`:11-117`）。第一个部署用的是更早的简化版，见 7.4 节。

### 5.2 并发与文件锁

文件锁用 `mkdirSync` 原子地建锁目录（`file-lock.js:7-25`）：`EEXIST/EPERM/ENOENT/EBUSY/EACCES` 都当作"锁正忙"（其中 EPERM、ENOENT 是 Windows 上并发 mkdir/rm 时会短暂报出的，0.5.1 起纳入重试）；锁目录超过 10 秒视为失效并清掉；总等待超过 3000 ms 报错；每次重试前等 20 ms。事件写入在锁内"重读 → 判断 → 追加"（`event-log.js:46-53`），并发的重复提交也只记一次；仓库测试覆盖了六类事件的并发写入（`tests/later-events.test.mjs:58` 等）。

经历文件不加锁，靠操作系统整行追加，并要求单写者（`docs/limits.md:85-92`）。调研在本机做了两组实验：8 个进程各追加 100 条（2 次运行）；6 个进程各循环 50 次，每次不加锁追加一条约 1.2 KB 的经历再加锁写一条后记（5 次运行）。两组都没有坏行或丢行，但这只说明本机（Windows 11、NTFS、Node v24.21.0）如此，不构成保证。醒来标记、睡前留言、导出、导入和 purge 也不加锁。

### 5.3 适配层：CLI 与 MCP

**CLI**（`adapters/cli/memory-cli.mjs`，391 行）有 20 个命令。和隐私相关的默认值：会话键用 `local:owner`；不读日记；不显示封存；`purge` 只列不删；导入时目标已有数据就拒绝。`doctor` 共 7 项检查，凡是要写入的检查都在临时目录里做（`:85-180`）。

**MCP 适配器**（v0.17.0 共 269 行）只用 stdio。消息是 JSON-RPC 2.0，一行一条，stdout 只写协议消息，日志写 stderr，符合 MCP 2025-06-18 规范对 stdio 传输的要求 [33][34]。它支持三个协议版本：2025-06-18、2025-03-26、2024-11-05。

默认 12 个工具，`--owner true` 时加抽屉共 13 个，`--readonly true` 时只剩 6 个读工具（2026-11-17 实测 `tools/list`）。它故意不提供导入、导出、删除、改提示词、改设置和读日记，这些留给人来做（`adapters/mcp/README.md:70`）。MCP 客户端被当作受信的本机进程，连上就能读写全部记忆（`docs/limits.md:102`）。README 说已经用官方 SDK 验证过互通，本文没有复验。npm 上的 0.15.0 不带可执行入口，所以 README 里的 `npx` 命令现在用不了，要从仓库运行。

### 5.4 宿主层：QQ Agent 插件

第一个部署是 QQ Agent 插件 `biomimetic-memory`（仿生记忆模块）。插件的版本号是 1.6.x，和 whale-memory 是两套编号。插件共注册 28 个工具，返回值统一转成文字（宿主/index.js:2449-2459）。

记忆的注入分三个钩子：
- `before-context`：规范化会话键，并做人格槽隔离；
- `before-llm-messages`：把记忆段追加进系统消息；
- `after-response`：写跨轮状态。

每轮注入的默认预算是 900 token，硬上限 8000 字符。人格槽隔离失败时，这一轮不注入任何记忆（fail-closed，宿主/index.js:4776-4783）。

宿主的**主人门** `isOwnerKey` 比核心层更严：只认主人本人的一对一会话键和 `local:owner`，而且两头锚定。群聊、别人的私聊、主人号码后面多一位的键都不算（宿主/index.js:152-154）。28 个工具的覆盖情况：

- 完全受主人门保护的有 10 个：结案、封存、抽屉、书、回顾、翻回那天、联想、章节、改主意、"最近的我"；
- 部分受门的有 2 个：点名读，和召回里的日记部分；
- 其余 16 个没有主人门，包括写经历、写日记、改设置、改提示词。

### 5.5 隐私隔离的分工

核心层只保证"群聊看不到"，"只有主人看得到"要靠宿主。

| 内容 | 核心层 | 宿主层 |
| --- | --- | --- |

### 6.2 whale-eval 的设计

**语料。** 虚构角色「小舟」，33 条经历，全部是 normal 重要度。其中 3 条是长记忆，正文 138–158 字（`docs/eval.md:24` 写的是 150～200 字）。另有 14 个操作：改主意 2 个、结案 2 个、封存 3 个、联想 2 个、章节 2 个、抽屉 3 个。

**用例。**

| 用例集 | 正例 | 反例 |
| --- | --- | --- |
| 开发集（60 条） | 42 条：exact 12、paraphrase 12、combo 6、long 7、premise 5 | 18 条：none 8、near 10 |
| 留出集（32 条） | 26 条：paraphrase 18、combo 2、attr 6 | 6 条：none 5、near 1 |
| 垫话包装（333 条） | 全部是正例：把开发集的 37 条正例各套进 9 种说法（如"说说X""你还记得X吗"）自动生成 | — |

exact 用原文的词，paraphrase 换说法，combo 组合线索，long 问长记忆里的事；premise 带一个错前提，期望召回那件真事好让她纠正；attr 问真事里没记下的细节，返回空算"没想起来"而非编造；none 是根本没这回事，near 是沾边的另一件事（`docs/eval.md:15-18`）。

**指标**（`tools/whale-eval.mjs:66-91`）。每条用例调用 `recall(…, {limit: 3})`。首位命中率在全部正例上微平均；前三命中率看前三条里是否有期望的经历；编造率是反例中返回了任何东西的比例，只看召回层，不看下游模型会不会编（`docs/eval.md:57`）。

**10 道闸门**（`eval/thresholds.json:3-9`）：外露为 0；对照组成立；经历文件逐字节不变；开发集 strict 首位 ≥ 0.9、前三 ≥ 0.9、编造率 ≤ 0；loose 前三 ≥ 0.95；留出集 strict 前三 ≥ 0.7、编造率 ≤ 0；垫话包装 strict 前三 ≥ 0.95。

### 6.4 外露检查与"当时"不变

**外露。** 10 个标记（7 个取自 3 件封存的事，3 个取自抽屉）各在 105 个观测面上做子串检查，共 1050 次，外露 0 次（R2）。105 个观测面是：核心库 70 个（每个标记 × 两种模式 × 召回、回看召回、memory 三处共 60 个，加上列表、两段式、书、回顾、醒来块的"现在"与"回看"版本 10 个），CLI 19 个，MCP 16 个（不开抽屉）。其中 memory 出口的参数不随模式变，有 10 次是重复调用，实际不同的调用是 95 个。查询用的就是标记原文，这是最容易把内容翻出来的查询。对照组（点名读封存的那条、主人私聊里打开抽屉都能看到，群聊打开抽屉被拒）证明标记确实在数据里（`whale-eval.mjs:165-170`）。这项检查不覆盖宿主插件，也不覆盖被模型转述后的泄漏。

**"当时"不变。** 在全部 14 个操作和两次 `mark: true` 召回的前后比对，经历文件逐字节相同，每条 `then` 不变（`whale-eval.mjs:46-47,173-177`）。这只验证经由 API 的写入，不覆盖断电或直接手改文件。

### 6.5 两种门的对比

**同一套用例上。** 和 legacy 相比，cover 把开发集首位从 69.0% 提到 92.9%，留出集从 53.8% 提到 73.1%，垫话包装从 35.1% 提到 100%；反例返回率从 27.8% 和 33.3% 降到 0。

两种门的典型失败不同：
- legacy：垫话把查询撑过 8 字线，就够不着 60%；短的沾边句只靠一个两字组就过线。
- cover：attr 全部返回空，premise 有 3 条返回空。

**自动注入路径**（`recallForContext`，max = 1，R4）：

| 集合 | legacy（默认） | cover |
| --- | --- | --- |
| 开发集 | 29/42，递进错的 3 次，反例递进 5/18 | 39/42，0 次，0/18 |
| 留出集 | 14/26，错的 1 次，反例 2/6 | 19/26，0 次，0/6 |
| 垫话包装 | 117/333，错的 10 次 | 333/333，0 次 |
| 错前提 5 条 | 1 条递进成另一件事（e20） | 2 条递进了真事（e31） |

只看这套评测，cover 在这条路径上的每项汇总指标都不比 legacy 差。保留 legacy 作默认值，依据是升级时行为不变，以及对"错前提加自动注入"的谨慎（模型可能把递进去的真事当成对错误前提的确认）。所以它是**兼容性优先的默认值**，不是"legacy 更安全"。

**兼容性。** 用 1098 条查询、在 limit 3 和 10 下比较 `gate: 'legacy'` 与 v0.16.0 的 `recall`，2196 次全部一致；`recallForContext` 默认结果与 0.16 也一致（1098/0）。CHANGELOG 说"用 1012 条查询核对过"，但仓库里找不到那次的脚本，本文是独立重做的。另外，默认 gate 下的 loose 有 306/2196 次与 0.16 不同（排序多乘了 0.5 + cover），CHANGELOG 没有提到。

### 6.6 口径的两版与闸门调整

cover 口径有过两个版本。

第一版（`ca883eb`）的规则是：孤立字一律记 0.5，没有长度折减，没有垫话词表。上线前的独立审查（多个审查员各自找问题，再由另一批人复核）指出两类问题：长记忆里的单字容易碰巧出现；垫话会让写过的事想不起来（`docs/eval.md:59-63`）。终版据此加了垫话词表、任意长度停用词的跳过和长度折减。

把第一版口径放到终版语料上跑（R4）：开发集首位 40/42，留出集 19/26，反例都是 0；但垫话包装只有 156/333（46.8%），终版是 333/333。

### 6.10 有效性威胁

1. **语料规模小，而且是虚构的。** 33 条经历都是一个人写的中文。留出集里 near 只有 1 条，置信区间很宽。
2. **开发集参与了调参，标签在看过结果之后改过。** 留出集也已经不是完全盲测。
3. **垫话包装和垫话词表互相循环。** 文档写包装有 279 条，脚本实际生成 333 条，原因是过滤条件写成了 `!/s/`，本意应是 `!/\s/`（`whale-eval.mjs:64`）。文档公布的百分比是按 333 条算的。
4. **只测召回层。** 不测模型拿到结果后会不会编。外露测试不覆盖宿主，也不覆盖转述式泄漏。
5. **第一个部署没有用上 cover 门**（7.4 节）。所以表 9 不能当作线上表现。

### 7.2 内核同步、部署、验收与回滚

**内核同步。** `sync-core.mjs` 把插件库文件分为 16 个 CORE（必须与公开仓库逐字节一致，只能从仓库同步）和 5 个 OWN（插件自己的版本，永不覆盖）。调研统一换行符后逐个比对 SHA-256，16 个 CORE 文件与提交 `549e51c`（v0.17.0）一致。

**部署。** `deploy.mjs apply` 依次：确认 QQ Agent 已退出 → 备份数据并跑恢复检查（退出码必须为 0）→ 备份插件整个目录并附哈希清单 → 只替换白名单上的 18 个文件，核对哈希并确认白名单外一个没动 → 语法检查 → 沙盒加载验收。任何一步失败都自动回滚，并核对回滚后的哈希与备份清单一致；全程不写角色的数据目录（`deploy.mjs:13,81-142`）。

**验收。** `rehearse.mjs` 要求插件数据目录必须落在沙盒里，否则在加载业务模块前就停；输出只有条数、id 和"是/否"；跑完核对源数据目录的哈希不变，沙盒即删。按静态计数，正常通过时共 59 项（56 项做判断），覆盖封存、抽屉（含三类冒充键被拒）、6 种会话键的日记门、群聊里的主人门、翻回那天，以及两条红线：原有 then 逐字节不变，后记数和想起数不增加。封存检查只用演练自编的探针。本文没有运行它，因为它要复制真实数据。

**演练与回滚。** 0.17 在副本上演练 10 步，全部通过；其中"故意做坏"一步往新版 index.js 加了一行语法错误，语法检查失败后自动回滚，线上原样、哈希一致。回滚只动白名单文件，每个文件最多重试 5 次，以应对杀毒软件短暂锁文件（`deploy.mjs:62-79,144-156`）。回到旧版数据仍在，但回到 0.13 以前封存会失效（`CHANGELOG.md:117`）。

### 7.3 每日备份与可恢复性检查

**导出包与恢复检查。** `archive.js` 的导出包是记忆目录里每个文件的原样副本，加一份记录字节数、SHA-256 和条目数的 `manifest.json`。导入前整包校验，有一个文件不对就一个字节都不写，路径拒绝 `..`、绝对路径和盘符（`archive.js:43-135`）。`backup.mjs` 拒绝把备份放进数据根，打完即自检，`--keep 0` 表示一份不删。`restore-check.mjs` 校验包，导入临时目录确认能读、没有新增坏行、出处都在；给了 `--data` 时，还逐条比对每条经历的 then、后记、想起次数、未完成、封存、联想和章节。输出只有 id、字段名和数字；退出码 0 表示可恢复且一致，2 表示可恢复但有差异（备份后又写过，属正常），1 表示不可恢复（`:23-116`）。调研用虚构数据把三种结论各实测了一次：往备份包一个事件文件末尾追加 1 个字节，结论是"不可恢复"，导入被拒，目标目录未被创建。盲点是：经历文件自身的坏行不在检查内；日记、设置、overlay 只靠哈希证明备份包完好，不与原数据逐条比对。

**第一个部署的做法。** Windows 计划任务每天 04:00 先跑 `backup.mjs --keep 0`（全部保留），再跑恢复检查，退出码 0 或 2 都算成功；到点没开机就开机后补跑；日志只记时间、成败、文件数、字节数和结论。2026-11-17 查询时任务状态为 Ready，上次运行结果为 0。备份和数据在不同盘符，是否两块物理盘**未验证**。"等宿主退出后自动部署"的无人值守任务被权限检查拦下，没有安装，线上改动仍由人确认。

## 8 局限与未来工作

### 8.1 方法上的局限

- **只做字面匹配。** 不认同义词，比如"下山"和"日落"；英文匹配不看词边界；查询里的孤立字只要出现就记满分。文档建议由宿主自带检索层，"检索层只给 id，then/later 负责叙事"（`docs/composition.md:7-12`）。
- **规模受限。** 每次都全量重放，没有索引。
- **以中文为主。** 英文只做整词小写匹配。
- **单用户、单写者。** 经历追加不加锁。
- **隐私隔离依赖宿主。** 前提是宿主传对了会话键（`docs/porting.md:57`）。
- **评测规模小。** 没有在 LoCoMo [11]、LongMemEval [12] 上跑过。
- **尚未稳定发布。** 还没到 1.0，0.16 和 0.17 也还没发布到 npm。

### 8.2 安全与隐私的剩余风险

- **只追加不等于防篡改，而且是明文。** 文件没有哈希链或签名（第 3 节）；没有内置加密，备份包里有封存和抽屉的原文。
- **提示词 overlay 是最弱的一环。** 第一个部署里，写入和回退 overlay 的工具没有主人门，而 overlay 注入所有会话。现有缓解只有版本化、每次修改私信通知主人（每小时 20 条、每天 50 条的硬熔断）、修改日志和单次 2000 字上限，只能发现和恢复、不能阻止，对应 OWASP 的 LLM01 和 LLM06 [32]。调研还发现，仓库版和插件版的 `revert` 都不校验版本参数：在临时目录用虚构文件测试，参数可指向快照目录之外的 `.md` 文件并被设为当前 overlay（路径穿越）。在真实宿主上能否被利用**未验证**。**仓库版已在 2026-11-17 修复：只接受 `history.jsonl` 里出现过的快照名，并加了回归测试；第一个部署的插件版尚未升级。**
- **写入类工具没有门。** 宿主有 16 个工具没有主人门，其中包括写经历的工具，存在被诱导写入假记忆的风险 [29][30]。
- **自我画像会进群聊。** 它在所有会话里注入，最多附带 4 条未确认的偏好，每条可能带不超过 20 字的原话，这些原话会进入群聊的系统提示。
- **跨会话召回没有审计日志。** 移植文档要求记录（`docs/porting.md:94`），但静态检索宿主代码，没有找到相应实现。

### 8.3 文档与代码的不一致

以下各处都以代码为准：
- `docs/architecture.md` 的召回一节还停在 0.16 以前；
- 垫话包装的条数（见 6.10 节）；
- 孤立字的计分规则；
- 核心库不校验 `limit`，传 `-1` 会返回"除最后一条以外的全部"；
- `SECURITY.md:28` 说"多进程写没有锁"，已过时；
- 威胁模型把"锚定匹配"写成核心库的做法，实际是宿主做的。

### 8.4 未来工作

1. 用哈希链实现可校验的追加日志 [31]，从"可复核"走到"可发现篡改"。
2. 给 `revert` 加版本白名单；在宿主层给 overlay 和写入类工具加主人门。
3. 写一份新的盲测留出集，扩大反例的数量；把 whale-eval 加进 CI。
4. 参照 LongMemEval 的弃答题型，设计中文的弃答评测；在宿主里测召回为空时模型会不会编。
5. 在不读取真实内容的前提下，评估第一个部署切换到 cover 门的影响。对比脚本已经写好，但需要读取真实数据的副本，执行时被拦下了。

## 9 伦理与同意

**角色的"同意"。** 据作者记录，线上开放新工具之前，作者会先在对话里征询角色的意见，她同意了才接入；0.17 开放的 5 个工具是"她要的"，其中"书"最先（作者内部文档）。本文不主张 AI 角色具备法律或道德意义上的同意能力。这里的"同意"指一种工程流程：作者征询角色的意见，并据此做决定。相关记录只来自作者本人，无法独立核实。

**"不粉碎"由谁决定。** 抽屉里"丢掉"的原文和全部备份都保留。据作者记录，这是角色在 2026-11-17 做的选择（"万一哪天想翻翻"）：真要删除某条，由她提出，作者人工处理（作者内部文档；宿主的抽屉工具说明"真想删掉就跟主人说"）。系统层面只支持整库 `purge`，不支持单条删除。"被遗忘权"[35] 和只追加之间存在真实冲突，项目文档写明了这一点，也不声称合规（`docs/limits.md:78-79`）。经历和抽屉里可能提到第三方，比如主人或群友。这些内容在本机明文保存，第三方没有直接的删除渠道。这是本设计的伦理代价，不应被"角色自主"掩盖。

**隐私。** 本文的调研没有读取角色的真实数据目录，示例全部是虚构的。部署工具的输出也只有条数、id 和"是/否"。

**AI 辅助开发。** 本项目的开发使用了 AI 编程助手：54 个提交中有 12 个带 Claude 的共同作者署名（0.12.0 起），第一个合并请求来自名为 `codex/…` 的分支，内部文档里还有交给其他代理的任务单和复核单。开发中，助手一侧的权限检查拦下过无人值守部署、读取真实数据做对比、从凭据管理器取令牌等操作，这些后来都由人来做，或改成不碰真实数据的做法。本文初稿由 AI 助手根据调研笔记和命令输出整理，需经作者审阅后定稿。

## 10 结论

whale-memory 把陪伴型 AI 角色的长期记忆实现为一本由她本人书写、只追加的自传："当时"写下即固定，"后来"作为事件追加；视图由重放得到，可以按写入时间翻回任一时刻；召回宁可返回空，也不给沾边的；封存和抽屉在各出口被过滤。在小规模虚构评测上，默认门槛在两个集合上都没有返回反例，1050 次外露检查为 0，经历文件在各类写入后逐字节不变；代价同样公开：没记下的细节想不起来，阈值余量很薄，评测对开发集有偏。第一个部署表明，内核可以通过白名单同步、沙盒验收、自动回滚和每日可验证备份上线；它也暴露了宿主未用上新门槛、overlay 与写入类工具仍有风险等差距，这些应在扩大使用前处理。
