# 上限与不保证

这份文档写清楚：它能撑多大、做不到什么、哪些是故意的。不想在 README 里写成"企业级"，也不想让你踩了坑才发现。

## 规模

实测（Windows 11 x64，Node v24.21.0，2026-11-16）：

| 经历条数 | `loadAll` 中位数 | `recall` 中位数 |
| --- | --- | --- |
| 2,000 | 4.9 ms | 13.9 ms |
| 10,000 | 21.8 ms | 68.3 ms |

复现命令（热身 3 次，取 5 次中位数；样本是 30~50 字正文 + 一句想法，1/4 带原文锚）：

```sh
node tools/bench-recall.mjs --n=10000
```

- 每次召回都会**读全量**、逐条扫描。没有索引、没有向量、没有分片。
- 一条经历约 0.5 KB，10,000 条约 5 MB。
- **事件文件只增不减**：每想起一次多一行 `recall-events.jsonl`，每改一次主意多一行 `later-events.jsonl`，每做一次「想通/暂放/再拾起」多一行 `unfinished-events.jsonl`（量很小）。上面的表只算了经历本身，长期使用要把这几份也算进去。
- 几万条会开始明显变慢；到十万级，这个实现就不合适了。

**故意的**：先保"原文不可改"和"没有记录就说没有"，再谈吞吐。要上十万级，宿主应当自己加索引（见 [composition.md](composition.md)），而不是把向量塞进这里。

## 存储与加密

- 明文 JSONL。**没有内置加密**，能不能加密取决于磁盘（BitLocker / FileVault / 全盘加密）。
- 任何能读这个目录的本机进程都能读全部记忆。多用户机器上，靠系统账户隔离。
- 没有多设备同步、没有云端备份。搬家靠复制整个目录或 `export`。

## 能力层验证，不是文件检查

`doctor` 不是看“目录在不在”，是在临时目录里真的走一遍：

```
写入 → 后记 → 结案 → 召回
导出 → 导入 → 读回
事件文件逐行解析
醒来白名单：私聊放行、群聊拦截
```

```sh
node adapters/cli/memory-cli.mjs doctor
```

`ok: true` 才说明这套代码在当前机器上真的能写能读。升级前后各跑一次；换机器也先跑它。

**关于索引**：本项目故意不做内置索引，原文是唯一真相。如果宿主需要索引（比如 FTS、向量），应当**在写入时旁路生成**，并且保证索引删掉后能从原文重建——索引永远不是来源，只是加速。任何“索引里有、原文里没有”的状态都算 bug。

## 提示词 overlay 是持久的（最特别的一条）

`prompt set` 写进去的内容会**每一轮都生效**，直到被改回。所以：

- 只允许可信的调用方（宿主自己、或在明确授权下的角色）改提示词，不要把用户的自由文本原样拼进去。
- 写之前先 `prompt get` 看当前版本，写完 `prompt history` 留底。
- 发现不对，立刻 `prompt revert --version <上一个版本>`。
- 提示注入一旦写进 overlay，不会随会话结束消失。这是本项目最容易被忽视的安全边界。

## 删除

**支持整库删除**，命令：

```sh
node adapters/cli/memory-cli.mjs purge --data <数据根目录>          # 只列出，不删
node adapters/cli/memory-cli.mjs purge --data <数据根目录> --yes true  # 真删
```

它只处理数据根目录下的这些位置：

- `plugin-data/biomimetic-memory/`（经历、日记、事件、设置、提示词 overlay）
- `plugin-data/biomimetic-memory.pre-import-*`（`import --force` 留下的备份）
- `backups/self-experience-pre-{later,recall}-events-*.jsonl*`（迁移备份）

**不处理**：`export` 的输出目录。导出包在你指定的地方，`purge` 不替你删，需要自己清理。

- **不支持单条删除**。`then` 故意不可改：能改就能洗记忆，"自传"也就不成立了。
- 因此"被遗忘权"和 append-only 有真实冲突。现在的答案是：**要忘就整库删，并且把导出目录一起删**；单条遗忘需要宿主自己设计墓碑或脱敏，本项目不提供。

## 并发

实际行为：

- `addExperience` **不加文件锁**，用操作系统的追加写（`a+`）。多进程同时写不丢行的前提是每次都整行追加；它不是事务，不能保证顺序。
- `later-events` / `recall-events` 的追加**走文件锁**（mkdir 互斥）；锁那一层的 mkdir 遇到 Windows 的 EPERM 会重试，**rename 不重试**。
- `self-settings` 和 `prompt` 的写是"锁 + 临时文件 + rename"。
- `export` / `import` **不加锁**：宿主还在写的时候导出，可能拿到一个文件新、一个文件旧的快照；导入时宿主还在写，也没有人拦。

因此：**导出、导入、purge 之前先停掉宿主**，或者接受快照可能偏几秒。不要让两个宿主进程同时写同一个目录。

## 召回语言

- 分词和停用词是按中文调的：中文按相邻两字切，常见虚词不参与匹配。
- 英文只做了最基本的支持：按整词、小写匹配，虚词过滤；不做词干、不做同义。
- 需要真正的多语言语义召回，请把检索交给宿主（见 [composition.md](composition.md)）。

## 不保证

- 不保证跨版本自动升级。改格式会写迁移脚本，但迁移前请先备份；迁移可以回滚，回滚会保留事件。
- 不保证"永远能读"。文件被手工改坏、事件被删、两个版本同时写同一个目录，都可能读不出来。
- 不保证角色"像人"。它只保证：当时写的没有被覆盖，后来的想法能追加上去，找不到记录时不编。

## 什么时候不该用它

- 需要语义检索、模糊匹配、跨十万条毫秒级召回
- 需要中文以外的多语言召回（英文只是够用）
- 需要多人协作、权限分级、审计日志
- 需要合规级加密与单条删除（GDPR 那类）
- 需要开箱即用的聊天记忆中间件

这些场景请用专门的记忆基础设施；whale-memory 只做"人格层"那一小块。不够用不是 bug，是边界。
