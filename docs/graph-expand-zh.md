## 一、借了什么

从"按字面匹配到一条就完了"扩展一步：这一条**连着的**几条，也可能是她在找的东西。

三种关系都来自她**已经写下**的结构，不是文本相似度猜的：

| 关系 | 来源 | 方向 | 说明 |
| --- | --- | --- | --- |
| `refs` | 记录的 `then.refs`（读出来是 `refsInfo` / `citedBy`） | 无向 | 写下时就知道的依据；引用方与被引用方互为一跳 |
| `link` | `link-events.jsonl`（`{from,to,reason}`） | 无向 | 后来亲手连的联想；两头都算 |
| `chapter` | `chapter-events.jsonl`（她给一段日子起的名字） | 组内互通 | `from ≤ day ≤ to` 落在同一段日子里的记录互为一跳 |

**只做 1 跳。** 2 跳开始就是"朋友的朋友"：几百条记忆里绕两步几乎人人相连，那就不是"想起"，是把半个库倒回给她。

## 二、默认关怎么证

1. **基线快照**：`tests/fixtures/graph-expand-baseline.json` 是在 `main` @ `7dc17fa` 的检出里生成的
   （12 条查询 × literal / hybrid × limit 10 的 id 序列），测试逐条比对；不传 `graphExpand`、
   或显式传 `graphExpand: false`，结果都必须与它逐条相同。
2. **评测数字**：`node tools/eval-v2.mjs --ranker=both` 在 main 与分支上各跑一次，两张表逐字节相同
   （只有耗时不同）。
3. **变异**：把 `recallInner` 的默认值从 `false` 改成 `true`，上面那条基线用例立刻变红（见第五节）。

## 三、为什么不插队

扩展只填**基础命中剩下的名额**：

```
基础命中 = [s1, s2]            （limit = 5，还剩 3 个空位）
扩展补入 = [c1, c2, c3]        （排在 s1, s2 后面，永远不会挤到它们前面）
```

由此有三个结构性保证（不是靠评测调出来的）：

- **recall@10 不会降**：原有命中的位置与内容一个都没动，只可能在空位上多出现一条期望条目；
- **MRR 不会降**：第一条命中的排名只看基础命中（或它在空位里被补到更靠后的位置，那也不需要）；
- **误召回率不会降**（也就是不会变多）：负例（`none` / `near`）基础命中为空 → 没有种子 → 不扩展，
  依旧 100% 返回空。

排序（`expandHits`）：

1. **命中了几条种子**（越多越可信：两条线索指到同一条 > 一条线索）；
2. **最好那条种子的排名**（第 1 名指的比第 9 名指的更相关）；
3. **时间**（新的先补，与字面检索的并列口径一致）。

补进来的条目带 `via: { seeds, seedCount, kind }`，宿主可以说清"为什么想起这条"；
`kind` 取最强的那层关系（`refs > link > chapter`）。

**补进来的不算"想起"**：`mark: true` 时只有基础命中写 `recall-events`，
扩展补的条目 `recalls` 不动——她没被问起这件事，是顺着别的线索想到的。

## 四、边界同样是硬约束

- **封存**：两层过滤（封存的行不进邻接表；指向封存记录的 `refs` / `link` 指针也不连）。
  只有调用方明确 `includeSealed: true`（她自己要翻）时才放开。
- **asOf**：邻接表就是从 `loadAll({ asOf })` 的结果建的，那之后才写下的邻居天然进不来；
  翻回那天不会因为"扩展"把后来的事带出来。
- **backend**：`file` 与 `sqlite` 走同一份 `rows`，扩展结果逐条相同（有测试）。
- **找不到的引用、重复 id**：不参与（邻接表里只留确实存在且唯一的两头）。

### 不撒谎的那一段：这轮数字一分没涨

开与不开，recall@10 / MRR 完全一样。原因查过了：

- 452 条用例里 **287 条**发生了补位，一共补进 **2559 条**邻居；
- 其中期望条目被补进来的：**0 条**；
- 正例被基础漏掉的有 **118 条**，其中只有 **5 条**的期望条目是种子的 1 跳邻居
  （全是 `chapter`），而且都排不进前 9 个空位；另外 **113 条**根本不是任何种子的邻居——
  排序再聪明也补不回来；
- 试过把 `chapter` 邻居的"时间"换成"离种子最近的日子"重排：被救回的仍然是 **0 条**。
  所以这版就按最简单、也和任务口径一致的"新的先补"，不为评测数字调参。

结论：这版证明的是**机制与边界**（默认关、不插队、不越权），不是**收益**。
真要收益，得让"期望条目在种子的 1 跳里"这件事更容易发生——那是线索表（T12）/ 章节质量的事，
不是这层排序能变出来的。宿主接的时候应当把扩展条目当"相关线索"，不要当"命中的答案"。

## 六、变异验证（抓到了哪条）

| 变异 | 变红的用例 |
| --- | --- |
| `graphExpand` 默认值 `false` → `true` | 默认关：不传 graphExpand 的召回与 main 基线逐条相同 |
| 扩展结果 `found.concat(extra)` → `extra.concat(found)` | 打开后不插队：前 N 条与关闭时逐条相同 |
| 拿掉「limit 已满」的两道闸（`size <= base.length` 的 guard + `slice(0, size - base.length)`） | limit 已经满 / 命中为空 / 没有邻居时，一条都不补（顺带排序那条） |
| 两层封存过滤一起去掉（行级 + 指向封存记录的指针） | 封存过滤：封了就不补 |

说明：单拿掉其中一道闸不会红（另一道还拦着）——这些用例守的是**行为**，不是某一行代码；
两层一起去掉才说明"这道防线真的在起作用"。

## 七、回滚

不传 `graphExpand` 就回到 0.27.0 的行为；这一版**没有改任何数据格式、没有新增事件类型**，
所以回滚不需要迁移，也不会留下需要清理的东西。

## 八、没验什么

- **真实数据目录**：只用临时目录与评测语料（`eval/corpus.json` / `corpus-v2.json`）。
- **规模**：邻接表每次召回现建；200 条（194 条可见）上实测建表 0.15ms、补位 0.24ms（20 次平均）。
  **万级没量**。章节很大时（一段日子几百条）扩展会往这一段里灌很多邻居，目前只有排序兜着，
  没有"每章最多补几条"的闸。
- **类型冒烟** `npm run types` 没跑：本机没有 `tsc`，`npx` 要联网。
- **跨平台**：只在 Windows / Node 24 上跑；Node 20 的 sqlite 对拍用例会 skip。
- **embed 排序**：代码分支也接了扩展，但没有单独量 embed（它是桩，本来就不当语义效果）。
- **宿主接线**：这一轮不接宿主，宿主传不传 `graphExpand` 完全由它自己决定。
